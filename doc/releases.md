# Releases

Implementation and release PRs target `coreweave`. Conventional Commits update a release-please PR containing only `CHANGELOG.md`, `version.txt`, and `.release-please-manifest.json`. The initial manifest records the upstream baseline, `2.3.0`; the bootstrap commit bounds the initial changelog to subsequent fork changes. Versions advance from those commits. Fork tags use `coreweave-v<major>.<minor>.<patch>`, so upstream tags and historical dirty tags cannot collide with automated releases.

Ordinary merges update the release PR and do not publish. Only the merge of a verified, approved release PR can publish. The release workflow verifies successful ordinary CI, human approval of the current head, and live acceptance evidence for the identical source tree and immediate parent of the actual merge. Stale head, stale base, failed cleanup, skipped tests, missing evidence, or a mismatched tree blocks publication. Squash merges are supported; publication uses the recorded merge commit rather than whichever branch tip happens to be newest.

## Administrator setup

Keep `RELEASE_AUTOMATION_ENABLED` unset until these steps are complete. Code can be reviewed and merged with automation disabled; it cannot obtain live credentials or publish a release in that state.

1. Set the repository default branch to `coreweave`. GitHub's `pull_request_target` uses the default branch; the verifier also requires the repository default branch to match the release target. Manual runs select `coreweave`.
2. Protect `coreweave` with required human PR approval, dismissal of stale approvals, the existing 22 CI checks, and the stable `storage-acceptance` check from GitHub Actions. Require Code Owner approval with a `CODEOWNERS` rule covering `*` that names human maintainers or a human team with write access; ensure automation cannot satisfy that ownership requirement. This protects ordinary implementation PRs as well as release PRs and is a precondition for enabling automation. Select the actual owners through repository administration. Require branches to be up to date before merging. Disable force pushes and protection bypasses. Use squash merges for release PRs and retain their Conventional Commit titles. Ensure workflow/control changes receive review. Block creation, update, and deletion of legacy `v*` tags; historical commits still contain the superseded tag workflows. Keep fork release tags immutable as well.
3. Enable the repository setting "Allow GitHub Actions to create and approve pull requests". This setting also permits other workflows with Pull requests write permission to approve PRs; generic required approvals alone do not guarantee human review. Configure the human Code Owner requirement above first. Release-please uses the built-in, short-lived `GITHUB_TOKEN` with Contents, Pull requests, and Issues write permissions. A separate job receives Actions write permission solely to dispatch validation. No App installation, App private key, personal token, or release-management environment is required. The release workflow never approves PRs or merges them.
4. Create the `storage-acceptance` environment with required human reviewers, prevent self-review, disable administrator bypass, and permit deployments only from the `coreweave` branch. Use the same controls for the `release` environment. PR merge refs, tags, and other branches must not be permitted to deploy. GitHub evaluates the trusted gate on the default branch; ordinary PR workflow code cannot use this branch-only environment.
5. Store `STORAGE_API_URL`, `STORAGE_ENDPOINT_URL`, `STORAGE_ORG`, `STORAGE_REGION`, and `STORAGE_OIDC_SUBJECT` as secrets on `storage-acceptance`, even when some are configuration rather than credentials. Obtain actual values privately. Do not store a CoreWeave API token, access key, secret key, or session token in either environment.
6. Bootstrap storage WIF as described below, then set `RELEASE_AUTOMATION_ENABLED=true`. Approve and observe the first protected release-PR gate before approving its merge. Verify that explicit dispatch ran all ordinary CI checks and the storage gate against the recorded candidate, that the created check's `external_id` round-trips as `<run ID>:<attempt>`, that storage exchange/renewal used OIDC, and that resources and private files were removed. GitHub may render a different check details URL; that display link is not used for authorization. Remove obsolete static storage-test secrets through the secret-administration path.

The branch and environment controls are part of the gate, not optional documentation settings. If configuration is incomplete, leave automation disabled. Repository settings, secrets, environment protection, and storage federation configuration require an administrator; the release workflow cannot configure them.

## Storage WIF bootstrap

Use local administrator credentials and a private cache outside the checkout. The QA token used for local validation must never become a CI secret. Inspect existing provider configurations and policies before adding resources; preserve unrelated policies.

Register an OIDC provider with issuer `https://token.actions.githubusercontent.com` and audience `https://coreweave.com/iam`, using released CWIC's `iam workload-federation oidc` commands or approved administration tooling. Read the repository's GitHub OIDC customization settings (`GET /repos/coreweave/s5cmd/actions/oidc/customization/sub`). Check whether the subject uses repository names, immutable IDs, or custom claims. Verify the actual `sub` issued for the protected `storage-acceptance` job privately. Set `STORAGE_OIDC_SUBJECT` to that exact value; the helper checks issuer, audience, and subject before exchange and suppresses mismatches without printing the token or claims. Do not grant wildcard repository or environment subjects.

Create a separate organization policy for that exact principal. Use `scripts/prepare_storage_wif.py --subject '<observed subject>' --output /absolute/private/path/policy.json` to prepare a mode-0600 proposal. Review it before applying it with the organization's approved local administration path. The proposal separates:

- `cwobject:CreateAccessKeyOIDC` on global resources `["*"]`.
- The suite's S3 actions on `s5cmd-acceptance-*` and `s5cmd-acceptance-*/*` only, including multipart, version deletion, and cleanup.

The principal format is `role/https://token.actions.githubusercontent.com:<observed subject>`. Storage federation is independent of the token used to manage PRs. The renewable login action is not yet available in the pinned public action revision, so the workflow uses the reviewed local OIDC process helper with pinned CWIC `v1.47.1` and pinned public CWIC setup action. Each renewal requests a fresh GitHub token. Replace the helper only with a reviewed, merged renewable action, preserving refresh and sanitization regressions.

## Gate operation

The trusted `Release` workflow runs release-please, verifies the resulting PR, and uploads an attempt-specific record containing only its source hashes and release metadata. After that producer job succeeds, it explicitly dispatches `ci` on the recorded release branch and `Storage gate` on `coreweave`. Both verify the immutable record against the trusted producer workflow run and its successful steps. CI checks its actual checkout SHA against the expected head before allowing builds or tests. This handles token-generated events without requiring an App or relying on approval of automatically generated PR workflow runs.

The trusted `Storage gate` workflow reads server-side metadata. An ordinary PR receives a successful `storage-acceptance` check without entering the environment or receiving OIDC permission. A release claim must match the built-in Actions bot identity, signed bot-authored commits, same repository, release target/branch, release metadata, increasing version, and the three permitted release files. Live execution additionally requires producer evidence bound to the current head and base. Spoofed titles, labels, branches, forks, human edits, and arbitrary source changes cannot authorize live execution. Automatic release-PR events do not replace the explicitly dispatched live check.

The gate records head, base, candidate merge, and tree hashes. It rechecks metadata after environment approval and before execution. Only the acceptance job has `id-token: write`. It checks out the verified candidate merge, runs the complete bounded live suite with renewable profile credentials and verified TLS, and attempts ledger-scoped recovery in an `always()` step. Private profiles and CWIC caches are removed even on failure. Raw build, storage, and credential-provider output is suppressed; public logs contain fixed outcomes and source hashes only. Do not enable Actions debug logging for these jobs.

Every release-please update dispatches new validation. Base-branch pushes invalidate the open release gate; release-please refreshes its PR and dispatches validation again, while strict branch protection prevents merging an outdated release branch. Superseded push handlers do not overwrite a newer base's check, and automatic PR-event runs use a different queue from explicit live dispatches. The completion job checks that head, base, and candidate content still match. Publication independently checks the producer record, the successful gate's trusted workflow run, all 22 successful CI checks from one explicitly dispatched CI run with a successful candidate preflight, and the actual merged tree/parent. The verifier also requires the head tree tested by CI to equal the candidate merge tree tested against storage and eventually published. A race between acceptance and merge cannot publish different content.

The completion job uploads only a small public source-hash record, separately named for each workflow attempt. Publication verifies that record and the successful live job/steps from the same trusted run. A copied check name or forged check summary cannot substitute for live execution. Evidence expires after 90 days; rerun the gate before merging a release with expired evidence.

## Reruns and cleanup

For a test failure, correct protected configuration or permissions privately and rerun all jobs of `Storage gate`. Partial "rerun failed jobs" attempts cannot reuse inspection evidence from an earlier attempt and deliberately fail the gate. If candidate recording or dispatch failed, rerun all jobs of the original `Release` run while its base is current, or run `Release` manually on the current `coreweave` tip to refresh the PR. Partial producer retries cannot reuse an artifact from an earlier attempt. For a revision change, allow the bot to update the release PR and approve the new gate; do not copy an older success. Release-please always rebuilds its branch after target-branch pushes, including changes without release notes. A rejected environment deployment or failed credential exchange remains a failed gate. Missing configuration cannot select fake storage.

For a CI failure, rerun all jobs of the explicitly dispatched `ci` run, including `release-preflight`. Publication requires the latest successful checks to belong to one such run. Ordinary manual or automatically generated PR runs cannot replace the candidate preflight, even if their check names match. If another CI run supersedes those checks, rerun the explicitly dispatched run before merging.

See [storage acceptance](storage-acceptance.md) for resource bounds and local validation. Recovery reads only the exact bucket in the run's new private resource ledger, never an account inventory or a prefix-wide sweep. Cancellation is not automatic on a superseding revision, allowing cleanup to finish. Deadlines terminate the process group gracefully and allow an additional cleanup window. Forced runner loss can interrupt cleanup and destroy its local ledger; use an approved private recovery record if that failure mode must be recoverable. Never upload profiles, caches, tokens, or resource ledgers to public Actions artifacts.

For local recovery with the original private profile/configuration and ledger, run:

```sh
go test -mod=readonly ./e2e -run '^TestAcceptanceRecovery$' -count=1 -timeout=4m
```

Recovery is a separate operation and cannot satisfy the release suite. Failed recovery retains the ledger and fails the job. Investigate service-side diagnostics privately; the public log deliberately omits raw HTTP responses and resource names.

## Publication and rollback

After authorization and release-environment approval, publication reserves the version tag at the verified merge commit and creates a draft release. GoReleaser builds archives, checksums, and Debian packages without publishing by itself; the workflow uploads them to that release and builds the existing multi-platform `ghcr.io/coreweave/s5cmd` image destinations. Binary and image builds use `version.txt` and the verified commit. Docker context excludes local credential and environment files.

The release becomes public only after binary upload and container publication succeed. Rerun the original `Release` run to retry publication of the same immutable merge/version. If its commit is no longer the current target tip, PR management is skipped so an older publication retry cannot rebuild the active release PR. Existing tags must still point to that commit; reruns cannot allocate another version. A completed public release skips rebuild, asset replacement, and image publication. Interrupted drafts are located by release ID and reused. Version and commit image tags are stable. `latest` and GitHub's latest-release pointer move only when the published version still matches the target branch's manifest, so rerunning an older release cannot roll them backward. A manually pushed tag does not invoke publication.

GitHub concurrency retains one running and one pending release run; a newer push can cancel an older pending run even with `cancel-in-progress: false`, including one waiting behind environment approval. If the cancelled run corresponds to a release merge, rerun all jobs of that original run to preserve its merge SHA. `workflow_dispatch` uses the current branch tip and cannot recover an older release merge. Check pending release runs when approving publication, and resolve an untagged merged release before proceeding with another release PR.

For rollback, deploy the desired immutable version or image digest. Do not rewrite released tags or replace acceptance evidence. Disable `RELEASE_AUTOMATION_ENABLED` to pause release management and publication, then revert through an ordinary reviewed PR and publish a new tested version. Leave required checks and environment protections in place.

## Local verification

Run `python3 -m unittest discover -s scripts -p 'test_*.py'`, focused Go recovery/configuration regressions, `make check`, and `actionlint`. Rehearse acceptance against isolated local storage and then the approved test service using local renewable credentials. GitHub environment enforcement, actual token-authenticated dispatch, and an actual GitHub-issued OIDC exchange require protected workflow validation; synthetic and local tests do not establish those properties.
